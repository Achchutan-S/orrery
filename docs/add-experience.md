# Adding an experience

The procedure. The rules it satisfies are the [Experience Contract](experience-contract.md); review a new experience against its [conformance checklist](experience-contract.md#12-conformance-checklist).

0. **Direction first.** Before anything substantial is built: a record in `docs/design/registry/<id>.md` with a brief and acceptance statements, a direction the owner approved, then one slice and its review ([creative process](design/creative-process.md), contract P0). Build the rest only after the slice is approved. `pnpm capture <id>` photographs it for review.
1. **Folder:** `apps/site/src/experiences/<id>/` (`[a-z][a-z0-9-]`). Routes live in `routes/`; layout, components, styles, content and assets beside them.
2. **Catalog entry:** `packages/experience-catalog/src/entries/<id>.ts` with `defineExperience({ … })`, and one line in `packages/experience-catalog/src/index.ts` (fields: [contract § 2.1](experience-contract.md#21-catalog-fields)). `title` and `summary` are also the default page title and description.
3. **Release:** nothing. With no entry in `config/release.json` it is an owner-only, unlisted draft: built locally and in previews, never in production. Never add a release entry just to see it. The repository is public, so a draft is off the website, not private.
4. **Routes:** canonical paths ([contract § 2.3](experience-contract.md#23-route-paths)) under `/<id>`; one route without parameters; dynamic routes with `getStaticPaths`. Every file the experience serves (PDF, image, download) is a route, never a `public/` file.
5. **Pages:** render `<ExperienceRoot experience="<id>">` (usually through the experience's own `Layout.astro`); styles in `@layer experience`, scoped by `[data-experience='<id>']`; flags with `flag()` in frontmatter and `data-pu-flag="<id>:<flag>"` on gated UI; links to other destinations only through `publicDiscoveryIndex()`. Wrap each React island's root in an error boundary (copy `sample-app/ErrorBoundary.tsx`); boundaries catch render, lifecycle and effect errors, not errors in event handlers or async code, which the component handles itself.
6. **Fonts, images and the Beacon:** follow [contract § 3.6](experience-contract.md#36-experience-owned-assets-and-fonts). Commit fonts (subsetted WOFF2, licence text beside each) and images (at the size and format they ship in) in the experience's folder and reference them from its CSS with `url()` or import the file: they ship as hashed, immutable assets ([ADR-028](adr/adr-028-experience-owned-fonts-and-images.md)). Do not use `astro:assets` optimisation: transformed images are refused by the leak check. A system font stack is a decision to justify in the direction record, not a default. Leave the Beacon's styles alone until a presentation mechanism exists ([contract § 3.5](experience-contract.md#35-the-beacon-platform-function-experience-presentation)).
7. **Link preview:** without `ogImage` the page uses the platform card `/og.png`. For its own 1200×630 image, add a route such as `/<id>/og.png` (`routes/og.ts`) and set `ogImage: '/<id>/og.png'`.
8. **Tests:** nothing to register: the generic accessibility, structure and reflow checks find its pages from the build ([ADR-027](adr/adr-027-derived-page-coverage.md)). Write its own tests for what is its own: unit tests for its logic and data, and a browser suite in `apps/site/test-browser/<id>.test.ts` with keyboard checks for every interaction. List every event it passes to `track()` in the catalog entry's `events`. Add it to `fixtureRelease()` only if a synthetic test needs it.
9. **Verify:** `pnpm typecheck && pnpm test && pnpm check && pnpm test:browser` (what CI runs). `pnpm build:production` must log `[pu:mount-experiences] production: mounted …` without the new id; `VERCEL_ENV=preview pnpm build` must include it. Then a local smoke test ([deployment.md § Against a local build](deployment.md#against-a-local-build---local)) and, after pushing, `pnpm smoke <preview-url> --env preview`.
10. **Publish** only after the prerequisites in [contract § 8.5](experience-contract.md#85-prerequisites-for-publishing-a-new-experience) are met and recorded (P0–P7: the approved direction and slice, accessibility coverage, a person's manual check in [accessibility.md § Results](accessibility.md#results), hosted CI on the pull request, the preview smoke test, the production build gate, the owner's approval, and the owner's approved final design review). Then change its release entry through `pnpm control` or a reviewed edit, in a pull request whose description names the review record ([ADR-029](adr/adr-029-ci-as-the-release-gate.md)).
