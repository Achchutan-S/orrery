# Adding an experience

The procedure. The rules it satisfies are the [Experience Contract](experience-contract.md); review a new experience against its [conformance checklist](experience-contract.md#12-conformance-checklist).

1. **Folder:** `apps/site/src/experiences/<id>/` (`[a-z][a-z0-9-]`). Routes live in `routes/`; layout, components, styles, content and assets beside them.
2. **Catalog entry:** `packages/experience-catalog/src/entries/<id>.ts` with `defineExperience({ … })`, and one line in `packages/experience-catalog/src/index.ts` (fields: [contract § 2.1](experience-contract.md#21-catalog-fields)). `title` and `summary` are also the default page title and description.
3. **Release:** nothing. With no entry in `config/release.json` it is an owner-only, unlisted draft: built locally and in previews, never in production. Never add a release entry just to see it. The repository is public, so a draft is off the website, not private.
4. **Routes:** canonical paths ([contract § 2.3](experience-contract.md#23-route-paths)) under `/<id>`; one route without parameters; dynamic routes with `getStaticPaths`. Every file the experience serves (PDF, image, download) is a route, never a `public/` file.
5. **Pages:** render `<ExperienceRoot experience="<id>">` (usually through the experience's own `Layout.astro`); styles in `@layer experience`, scoped by `[data-experience='<id>']`; flags with `flag()` in frontmatter and `data-pu-flag="<id>:<flag>"` on gated UI; links to other destinations only through `publicDiscoveryIndex()`. Wrap each React island's root in an error boundary (copy `sample-app/ErrorBoundary.tsx`); boundaries catch render, lifecycle and effect errors, not errors in event handlers or async code, which the component handles itself.
6. **Fonts, images and the Beacon:** follow [contract § 3.6](experience-contract.md#36-experience-owned-assets-and-fonts). Today the production output allowlist rejects hashed font and image files imported from an experience (decision D11), so use system stacks, the platform face or the experience's own file routes. Leave the Beacon's styles alone until a presentation mechanism exists ([contract § 3.5](experience-contract.md#35-the-beacon-platform-function-experience-presentation)).
7. **Link preview:** without `ogImage` the page uses the platform card `/og.png`. For its own 1200×630 image, add a route such as `/<id>/og.png` (`routes/og.ts`) and set `ogImage: '/<id>/og.png'`.
8. **Tests:** add the id to the pinned lists in `tools/checks/src/metadata.test.ts` and `apps/site/test/pipeline.test.ts` (`folders`, and `PAGES` with every page it builds); add its own pipeline assertions; add its page types to the browser suites (`apps/site/test-browser/`) with axe and keyboard checks for anything interactive. Add it to `fixtureRelease()` only if a synthetic test needs it.
9. **Verify:** `pnpm typecheck && pnpm test && pnpm check && pnpm test:browser` (what CI runs). `pnpm build:production` must log `[pu:mount-experiences] production: mounted …` without the new id; `VERCEL_ENV=preview pnpm build` must include it. Then a local smoke test ([deployment.md § Against a local build](deployment.md#against-a-local-build---local)) and, after pushing, `pnpm smoke <preview-url> --env preview`.
10. **Publish** only after the prerequisites in [contract § 8.5](experience-contract.md#85-prerequisites-for-publishing-a-new-experience) are met and recorded (P1–P6: accessibility coverage, a person's manual check in [accessibility.md § Results](accessibility.md#results), hosted CI on the publishing commit, the preview smoke test, the production build gate, the owner's approval). Then change its release entry through `pnpm control` or a reviewed edit.
