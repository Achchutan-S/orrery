## Growing in steps

<Claim standing="planned">

The blueprint orders the future in phases. Each one begins only when the one before it is finished and something real needs it. Nothing below exists yet.

</Claim>

<ol class="phases">
<li>

**Phase 1: the platform experience.** A real home page and the Beacon, a small identity mark with a command palette for moving around (both built, chapter 7); the resume with a downloadable PDF (built as a draft awaiting approval, chapter 7); a first piece of writing; a first real interactive experience; UI Lab and Dev X-Ray on subdomains of the platform's own domain; privacy-respecting page analytics with a privacy page; and the first version of the Control Center. The samples are deleted then; the canary stays.

</li>
<li>

**Phase 2: publishing and discovery.** The writing collection with tags, related entries, a feed, a sitemap, link-preview images generated for each entry and a search index, all built from what is actually published.

</li>
<li>

**Phase 3: governance and observability.** A more complete Control Center (promotion checks, archiving with redirects), anonymous usage events through `track()`, error reporting for interactive experiences, and a rehearsed rollback.

</li>
<li>

**Phase 4a: owner identity.** Sign-in for one person, the owner. The Control Center moves to its own subdomain, and the first pages rendered per request appear, behind `authorize()`.

</li>
<li>

**Phase 4b: audiences.** A small database for invitations, grants, sessions and an append-only audit log; private experiences shared with chosen people; a personal "shared with you" page; feature flags for specific audiences.

</li>
<li>

**Phase 5: advanced experiences.** Experiences that outgrow the shared build move to their own deployments while keeping their addresses, and an exploratory view of everything appears once there are enough experiences to explore.

</li>
</ol>

## The Control Center

<Claim standing="implemented">

The operations it performs (changing a lifecycle stage, access, discoverability, a flag or a note) are written as pure, tested functions in the schema package, with the rules for which lifecycle changes are allowed. The Control Center is an interface to those functions, not a second set of rules.

</Claim>

<Claim standing="verified">

The first version exists on the owner's machine and passes its tests (tasks 12 and 13): a local server and an interface for it, started together with one command. The server listens only on the owner's own machine, answers only to its own addresses and to requests from the Control Center page, and needs a session that ends when it stops. The interface shows every experience and what each environment would do with it, previews every change on the server, says in plain words what production would gain or lose, and writes only after confirmation. A change is refused if the file changed since it was loaded, so it never overwrites a newer edit. It never runs Git and is never deployed: publishing is still a commit the owner makes.

</Claim>

<Claim standing="planned">

A later version moves the Control Center to its own subdomain behind owner sign-in and records each change as a commit. Until then committing stays a manual, visible act.

</Claim>

## This Journal

<Claim standing="implemented">

The Journal is an experience like any other. Its chapters live in the repository; whether it is built, listed or hidden is decided by its entry in `config/release.json`. Withdrawing it is an edit to that entry, not a deletion, and the Control Center manages it through the same functions as everything else.

</Claim>
